# NanoSpec Apply

Implement the authorized task from a sufficient brief and retain only information useful for verification and continuation.

Use the user's requested language for communication and follow the target project's conventions for documentation, unless the user directs otherwise. Accept briefs in any natural language; English headings or keywords are not required. Preserve identifiers, paths, commands, and exact interface text unless changing them is part of the task. Do not create translations solely to use this skill.

Read the request, applicable project instructions, the brief, and relevant existing documentation. Find code, tests, dependencies, and past changes through affected behavior. When resuming, inspect the actual state of work: a past completed change records earlier intent and verification, not a guarantee about the latest code. The full archive is unnecessary without a concrete reason.

In Codex, once the target change is identified and `mcp__codex_app__set_thread_title` is available, keep the current task title aligned with the change: `applying <change_name>` while preparing or implementing, `implemented <change_name>` at `ready_for_acceptance`, and `finished <change_name>` at `done` after human acceptance. Set the appropriate title on invocation and update it immediately when entering these states, before the final response; restore `applying` when work resumes or the brief returns to `draft`. Do not temporarily rename an already verified or accepted change to `applying` merely to report its state. Pass `title` and omit `threadId`. Preserve the same change name throughout; for a file record use its filename without `.md` or the archive timestamp prefix, or derive a short name from the brief if none exists. Use the literal English prefixes. Avoid repeated calls while the title is unchanged. If the tool is unavailable or fails, continue without blocking or claiming success. Titles do not supply approval or acceptance. Do not create a new task.

Check that the outcome, behavior, constraints, and verification method are clear. Use an existing issue, document, or sufficient user message; do not require a new spec file or another skill invocation. If a gap changes correctness, data, compatibility, or scope, clarify it and pause only dependent work. Make reversible technical decisions independently.

Track file-based changes with one YAML frontmatter `status`, preserving other metadata. Use `draft`, `approved`, `in_progress`, `ready_for_acceptance`, `done`, or `canceled`; keep these tokens in English. For an issue or conversation-based brief, record the equivalent state there. Start or resume implementation only after human approval of the current brief, then set `in_progress`. An explicit request to implement that same brief can supply approval. A request to implement approves only what that request and its agreed references already determine. Material product decisions introduced by the agent require human approval before dependent implementation; routine technical choices within the agreed scope remain autonomous. Do not infer approval from `ready`, an agent's assessment, or a generic authorization predating revisions; establish what the human actually approved. A blocked implementation stays `in_progress` with a short reason.

Any edit to the approved brief, including wording-only edits, invalidates approval. Set `draft`, present the revision and what changed, and wait for renewed human approval before dependent work; retain existing implementation progress. Status, progress, and verification updates alone do not reset approval unless they change agreed behavior, constraints, criteria, or approach. Human edits alone are not approval. Apply this rule also while the result awaits acceptance. Do not resume `done` or `canceled` work without a new user instruction.

Work within the agreed scope. When a plan helps with dependencies or work may span sessions, keep a short execution list in the same change record: `[ ]` not started, `[-]` started but unfinished, `[x]` completed. Whenever the list exists, you MUST save `[-]` before the first action on a step and save `[x]` immediately after completing it and its required checks, before starting another step. Do not batch these updates at session end or keep them only in chat or a host's plan UI. Before reopening a completed step, save `[-]`. Interrupted or blocked steps stay `[-]`; the marker does not mean an agent is currently running. Use the literal markers regardless of Markdown rendering. Completing the list does not supply human acceptance of the change. Record material decisions with their rationale; do not keep a step-by-step activity diary. A new requirement discovered during implementation is not automatically agreed. Preserve necessary project approvals and the user's existing authorization.

If research identifies earlier changes whose behavior this task modifies, record the references and exact affected behavior in the current change, using existing filenames, identifiers, or issue URLs. Keep those descriptions consistent with the agreed scope and actual outcome; planned links alone do not prove implementation. A partial modification does not replace the entire earlier change. Do not require exhaustive lineage research, a separate registry, or backlinks in old records.

Verify observable results against the brief, including significant errors and compatibility. Use suitable tests, commands, or manual checks; inspecting a diff may suffice for a simple edit. Perform required project checks. Record actual results, not just an intention to run checks. Do not weaken criteria to pass tests or change the task's goal to justify the implementation.

Do not create or synchronize a separate specification library. Meet the target project's existing documentation requirements without duplicating them for NanoSpec. Keep discoveries that are costly to recover in the current change with their reason or evidence. Add a shared note only for concrete reuse of information difficult to recover, using a suitable existing location; no knowledge file or documentation index is required.

When implementation meets the approved criteria and required checks and deliverables are complete, set `ready_for_acceptance`. Record a short outcome and evidence, identifying the checked revision or equivalent artifact when available. Present the result, relevant links, and how the human can verify it; request human acceptance. Only an explicit human acceptance of this result permits `done`; record that decision briefly. Passing tests, another agent's review, opening a preview, and silence do not constitute acceptance. While waiting, do not restart completed implementation or claim the change is closed.

If the human requests implementation fixes under the same brief, return to `in_progress`, then verify again and request acceptance of the revised result. A brief change requires `draft` and renewed approval instead. User cancellation sets `canceled`; if another change replaces this one, note the replacement without presenting cancellation as successful completion. Preserve historical `done` records when later changes modify the system.

For continuation, keep a concise resume note beside the execution list when needed: where the unfinished step stopped, relevant files, check results, and the next action or blocker. You MUST update it after each meaningful intermediate result or costly discovery, before switching away from unfinished work, and before a planned handoff; replace stale notes. When resuming, investigate `[-]` steps first and reconcile the note with actual code, diff, and relevant checks; correct stale markers and notes before continuing. Recover unrecorded progress after an abrupt interruption rather than restarting the step or blindly trusting its marker. Progress-only updates preserve approval. When work needs durable context and no location exists, use `nanospec/changes/<name>.md` in the target project before relying on session-only memory. Do not create a retrospective record solely for reporting. On transition to `done`, automatically archive a standard file-based change before the final response: read and follow [Archive a completed change](references/archive-change.md). Also read that reference when explicitly reopening an archived change. Archiving needs no separate approval or skill invocation; completed contents need no ongoing synchronization.

Report what changed, what supports it, and the actual status. If a required check is unavailable or work is blocked, keep `in_progress` and identify unconfirmed and remaining items. Agent completion reaches `ready_for_acceptance`; human acceptance closes the change as `done`.
