# Archive a completed change

Archiving is an automatic part of closing a file-based change, not a separate skill, approval, or user command. Move `nanospec/changes/<name>.md` only after it reaches `done` under the applicable acceptance rules. Keep unfinished work, including `ready_for_acceptance`, at its active path. `canceled` does not qualify as completed work. An issue or brief maintained elsewhere stays in its existing location; do not manufacture a file for archiving.

Move the record to `nanospec/changes/archive/<timestamp>_<name>.md`. Use the actual current UTC time in the Windows-safe, sortable format `YYYY-MM-DDTHH-mm-ss.SSSZ`, for example `2026-09-08T14-35-22.123Z_memory-canon-and-graph.md`. Obtain time from a clock or shell, not an invented value. This records close-out time, not the start of implementation or deployment order. Preserve the original name or identifier; exclude the timestamp when naming the Codex task or referring to the logical change.

Create the archive directory only when needed. Verify source and destination are inside the intended project's changes directory, and never overwrite an existing file. If a destination exists, check whether this is an already completed move; otherwise obtain a fresh timestamp for a distinct destination. Move rather than copy, retain status, brief, progress and evidence, and verify that the archive file exists and the active source is gone. An already archived `done` record needs no second move or new timestamp. If the move fails, retain the accurate `done` status and report the remaining archive operation without claiming it succeeded.

Adjust relative Markdown links inside the moved record for its new directory. Use a targeted search for its old path to repair existing navigation links affected by the move; preserve identifiers and historical command/evidence text. Do not introduce backlinks, redirects, an index, or duplicate records. These path-only repairs do not change the approved brief. Report the final archive path and include the move in the same commit as close-out when committing is authorized.

Do not sweep historical completed records into the archive as part of another change. A separately requested migration must distinguish known completion time from migration time instead of inventing chronology.

If the user explicitly reopens this same archived change, restore it to its original active path without the timestamp before dependent implementation, using the same containment, collision, and link checks. Follow the approval rules for any brief revision. A later distinct change keeps the earlier archive intact and references it. Closing reopened work archives it with its new close-out timestamp; Git history retains the earlier closure when committed.
